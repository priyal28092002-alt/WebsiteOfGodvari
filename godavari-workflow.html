Animated Sequence Diagrams
UML-style lifelines showing exact message order between components

Sequence diagrams capture who calls whom, in what order, and what is returned — the single most common whiteboard exercise in a Java architect interview. Each vertical lifeline is a participant (client, gateway, service, datastore); each horizontal arrow is a synchronous REST call or database operation, read top-to-bottom in the order they occur.

Containers share a user-defined bridge network so services resolve each other by container name (e.g. http://order-service:8083) instead of hardcoded IPs — Docker's embedded DNS handles resolution, while Eureka additionally provides logical, load-balanced service names to the application layer.

In production the same containers are deployed to Kubernetes for self-healing, horizontal scaling and rolling, zero-downtime upgrades.

Circuit Breaker (Resilience4j)▼

Wraps a remote call and tracks failure rate. Once failures cross a threshold the breaker trips OPEN and short-circuits further calls immediately (returning a fallback) instead of letting threads pile up waiting on a dead dependency. After a cool-down it goes HALF-OPEN to test recovery before closing again. Without it, one slow/dead service can exhaust the caller's thread pool and cascade the outage upstream — this is the #1 microservices interview follow-up question.

Retry Pattern▼

Transient failures (a brief network blip, a pod restarting) are retried automatically with exponential backoff + jitter so a fleet of clients don't retry in lockstep and hammer a recovering service. Retries are only safe for idempotent operations (GET, PUT) — retrying a raw POST /orders without an idempotency key can create duplicate orders.

Graceful Degradation / Fallback▼

When Redis is unreachable, Product Service falls back to querying MySQL directly instead of failing the request — slower, but still correct. When Inventory Service is down, Order Service can accept the order in a PENDING_STOCK_CHECK state rather than rejecting the customer outright. The system prefers a degraded response over no response.

Timeouts & Bulkheads▼

Every inter-service HTTP client sets an aggressive connect/read timeout so a hung dependency fails fast rather than blocking indefinitely. Bulkheading isolates the thread/connection pool used to call each downstream service, so a saturated Inventory Service can't starve the pool used to call Billing Service.

Observability Stack

Metrics alone tell you that something is wrong; logs and traces tell you why. Godavari's stack combines all three pillars of observability:

📈 Prometheus + Micrometer▼

Micrometer is a vendor-neutral metrics facade embedded in Spring Boot Actuator; Prometheus scrapes each service's /actuator/prometheus endpoint on an interval and stores it as time-series data — request counts, latency histograms, JVM heap, thread pool saturation.

📊 Grafana▼

Turns Prometheus data into dashboards and alerts — e.g. "page on-call if p99 latency > 500ms for 5 minutes" or "error rate > 2%". This is the dashboard an SRE watches during a release.

🔍 ELK Stack (Elasticsearch, Logstash, Kibana)▼

Centralizes logs from all 9 services + gateway into one searchable index, since SSH-ing into 9 containers to grep logs doesn't scale. Structured JSON logs are correlated by a request/trace ID so one customer complaint can be traced across every service it touched.

🕸️ Zipkin / OpenTelemetry▼

Distributed tracing: a single trace ID is propagated through Gateway → Order → Inventory → Billing, and each hop reports its span (duration + parent). This turns "checkout is slow" into a flame graph pinpointing exactly which service ate 400 of the 420ms.

💓 Spring Boot Actuator▼

Exposes production-ready endpoints out of the box — /actuator/health (used by Kubernetes liveness/readiness probes), /actuator/metrics, /actuator/info — with almost zero extra code.
